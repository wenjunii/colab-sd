# Security and dependency scope

## CPU checks

`requirements-test.txt` is used by GitHub Actions and the offline model stand-ins. It uses Torch 2.13.0 and Transformers 5.10.1 to address the 27 Dependabot alerts reported against the previous Torch 2.5.1 and Transformers 4.39.3 pins. Transformers 5.10.1 requires Hugging Face Hub >=1.5,<2; keeping the old Hub 0.25.2 pin prevents installation. FastAPI is upgraded with its compatible Starlette dependency as well. The wider installed-package audit also requires Pillow >=13, filelock >=4.2.1, and setuptools >=84.1.0. Patched Pillow and filelock require Python 3.11, which is now the development and CI baseline.

The workflow installs these requirements with the official PyTorch CPU wheel index in one resolver transaction, runs `pip check` before the tests, and audits the installed environment with `audit_dependencies.py` and `pip-audit`. Future Torch updates therefore also update the wheel selected by CI, without a second version pin in the workflow. The audit reports newly published vulnerabilities as CI failures instead of suppressing alerts.

`pip-audit` cannot look up Torch's local `+cpu` version on PyPI. The audit helper therefore creates an exact inventory of the installed packages, maps only the official Torch `+cpu` build to its base release, and audits that inventory without resolving or installing packages again. Other local builds are rejected. Skipped or missing audit results fail the check so an unaudited package cannot silently pass.

To audit the installed development environment:

```powershell
.\.venv\Scripts\python.exe -m pip install pip-audit==2.10.1
.\.venv\Scripts\python.exe audit_dependencies.py
```

## GPU runtimes: known legacy dependencies

`colab_setup.py` embeds a separate runtime setup in the generated notebook. It still installs Diffusers 0.24.0, Transformers 4.39.3, Hugging Face Hub 0.25.2, and Accelerate 0.30.1 for compatibility with the pinned upstream StreamDiffusion wrapper. The runtime also retains Colab's installed CUDA build of PyTorch, which may be older than the CPU test version. These versions are not security-current. A clean Dependabot view for the test manifest must not be interpreted as a security audit of the Colab runtime.

The bridge uses SD-Turbo and TinyVAE; it does not offer a client control for selecting arbitrary model repositories or enabling remote model code. Continue to use trusted model sources and do not load untrusted Python, pickle/checkpoint files, tokenizers, or model repositories into this runtime. Model-source restrictions reduce exposure but do not patch vulnerable dependencies.

The remaining GPU migration must update the dependency stack together, verify model loading and non-flat image output in both generation modes, check prompt blending and denoise strength, and validate both TensorRT UNets against native outputs. Test-only dependency updates do not establish GPU compatibility. The last GPU validation and its exact software versions are recorded in the README.

TensorRT deployment archives contain executable model graphs and must come from your own trusted runtime. Keep Drive/cache folders private; checksums detect accidental corruption, not a malicious replacement of both archive and manifest. The cache validates hardware/software/model metadata and numerical output before use. Stripped/refit engine caching remains disabled.

## Optional SDXL-Turbo selection

The normal StreamDiffusion runtime accepts only `sd-turbo` or `sdxl-turbo` at startup; clients cannot choose an arbitrary repository or model revision. SDXL loads the pinned official safetensors model and matching pinned TAESDXL with no remote model Python. It uses the same legacy Diffusers/Transformers environment described above; selecting XL does not remediate that stack's known vulnerabilities. Native GPU loading and XL TensorRT graphs still need hardware validation. The CPU execution probe uses disposable legacy packages and randomly initialized tiny components without pretrained weights, and does not alter the reusable test environment.

Application and weight licenses are distinct: the SDXL-Turbo model repository lists `sai-nc-community` and refers commercial users to Stability AI's separate licensing terms. The bridge does not grant unrestricted commercial model rights. Exact model/TinyVAE revisions and source links are recorded in the README and adapter. Existing SD-Turbo/Waypoint/Krea selections remain available.

XL TensorRT graphs retain pooled text and image-size tensors as inputs. Export/load validation includes altered prompt inputs, and native model weights/configuration remain part of the cache fingerprint. Keep deployment archives and model caches trusted/private as described above. The launcher's readiness check rejects an SD-Turbo server when SDXL-Turbo was requested; loading/compilation failure does not publish another model as a successful launch.

## Optional Waypoint runtime

`Waypoint_Colab_Server.ipynb` installs `waypoint_setup.py` dependencies in a separate environment, rather than replacing SD-Turbo's compatibility stack or the notebook kernel. The runtime source is pinned to a Git commit. `waypoint_backend.py` downloads only the pinned official model's configuration/safetensors and the pinned official TAEHV checkpoint; no client-selected model code is loaded. The TAEHV runtime reads a trusted PyTorch checkpoint. Keep model cache folders private and do not substitute untrusted checkpoints.

Waypoint currently requires Torch 2.11.0 upstream, plus its quantization/compiler dependencies. The CPU suite uses a different, newer Torch version. Its dependency audit does not cover this optional GPU environment or establish A100 compatibility. The installer runs `pip check` and a CUDA/import preflight; those are dependency/availability checks, not vulnerability or image-quality checks. Some transitive dependencies remain resolved by upstream constraints. Cloudflared uses the official release download, matching the existing launcher setup.

The world-mode controls, seed uploads, delivery credit handling and reconnect lifecycle have CPU contract tests. Basic A100 40 GB INT8 generation with the fast profile and an existing VM/cache is recorded in the README; other profiles and long-running operation still need live checks. The model is image-conditioned. Optional prompt seeds load only the startup-selected `sd-turbo` or `sdxl-turbo` official safetensors model through Diffusers 0.39.0 inside the Waypoint environment. The revisions are fixed in `waypoint_seed.py`; SDXL uses `71153311d3dbb46851df1931d3ca6e939de83304`, matching the standalone adapter. Both retain their original VAE. Prompts create starting images instead of directly conditioning the world model. The modern dependency stack meets the existing Hub/Transformers constraints. CPU contract tests and real tiny-component SDXL execution do not establish full-model GPU loading, combined GPU behavior or a complete GPU-environment vulnerability audit. No client-selected model repository or remote model code is enabled. A readiness check rejects a server reporting another seed model when SDXL was requested.

Waypoint and the selected seed generator share the existing worker, controller slot, and optional token authentication gates. Seed generation waits for output credit and is bounded to one reseed at a batch boundary; missed timer ticks do not accumulate. An automatic seed failure stops automatic retries. The Colab notebook defaults to a blank token, as does the SD-Turbo notebook; anyone with its tunnel URL can attempt to connect.

## Optional LTX-2.5 clip trial

The LTX application source is Apache-2.0 at `4f521619ae0029e8fbb64d555030c2b121a33b4f`; its archive SHA-256 is pinned. Extraction checks path containment, symbolic links, required files and size/count limits. A source receipt verifies cached files before reuse. The model distribution is separately pinned to `Lightricks/LTX-2.5` revision `49b093a39c19169a8a81721dcc541e07e945232f`, under the LTX-2.x Community License (amended 2026-10-29). Commercial eligibility depends on that license; entities with at least $10M aggregate annual revenue generally need a paid license for commercial use. Apache application code does not grant Apache rights in the weights. The README links the exact distributions and terms.

Only five selected split checkpoint files are requested. Byte counts and LFS SHA-256 hashes are pinned; the existing cache helper validates and stages them locally, including Safetensors headers. Access is checked before large downloads. Hugging Face access must already have been accepted by the user; the notebook does not accept model terms or store a token in source, logs, Git or Drive. An existing HF credential or the Colab HF_TOKEN secret is passed through the process environment. Valid caches and other backend environments are preserved.

The trial uses an isolated Torch 2.11/CUDA 13.0 environment, FP8-cast storage, CPU offloading, the convolutional VAE and no optional custom CUDA build. Pipeline construction precedes lazy GPU weight loading; readiness is not a successful inference assertion. A controller must negotiate ACKs, configure Prompt A and explicitly request Generate or Restart before continuous generation is armed. At most one bounded CPU clip plus delivery credits is queued; the optional next seed is one PNG inside an owned temporary directory, removed on disconnect/shutdown. Continuous Off, Pause and disconnect stop further scheduling according to the documented current-work boundary. Failures disarm rendering until another explicit request. The resident profile retains a single quantized transformer allocation and one prompt embedding; a changed prompt releases transformer weights before text encoding. The resident profile loads Gemma on GPU only after releasing DiT, and disposes Gemma before loading DiT. The lower-memory profile streams both large models from CPU. No unsafe compilation-cache guard override is enabled. CPU tests/source contract checks do not establish GPU correctness, installation compatibility, quality, performance or a complete GPU-dependency security audit. The README distinguishes observed GPU measurements from CPU build/import contracts; other profiles and long-running behavior need separate GPU validation.

## Optional Krea HF modular runtime

The commercial-use requirement excludes the CC-BY-NC-SA Krea GitHub application. The Krea notebook instead targets the separate official HF release at revision `9a2ceea280e5d584c6a28d384a9c19e38c810f8c`, whose model card declares Apache-2.0; modular blocks retain their Apache-2.0 headers and transformer files retain upstream attribution. Supporting Wan components use revision `38ec498cb3208fb688890f8cc7e94ede2cbd7f68` (Apache-2.0). See the README's source/license links. A model-card declaration does not change the separately licensed GitHub application or establish terms for unrelated distributions.

This backend deliberately executes custom model Python. `krea_assets.py` downloads only named source/config files and safetensors shards, verifies the 14 source/config SHA-256 hashes, and only then permits `trust_remote_code=True` for those local files. `krea_weights.py` validates all nine weight sizes/SHA-256 hashes against the recorded pinned Hub LFS metadata and parses Safetensors headers while staging to the VM's local disk. Inference loads these local files, not Drive-mounted checkpoints. A matching trusted-local receipt uses size/mtime/ctime plus the expected digest to reuse a previously validated copy; changing or removing a receipt causes full validation. A bad persistent checkpoint gets one Hub `force_download` retry for that exact repo/revision/filename; valid caches and unrelated models are not deleted. Partial staging is owned temporary scratch and completed staged files remain reusable after interruption.

Wan components load locally with remote-code trust disabled and safetensors required for weights. The browser/TD client cannot choose a model, source revision, code URL, or runtime path. Persistent model files, local validation receipts and private module caches must remain trusted. These integrity checks establish the recorded file versions, not a complete supply-chain audit of model behavior or installed dependencies. No unpinned attention kernels are downloaded.

All 24 non-weight assets also have pinned sizes/SHA-256 values; JSON metadata must parse before use. Legacy text-link resolution requires the expected Hub repo/revision layout, accepts only relative hash-named blob paths within that cache's repo/shared blob stores, rejects escapes/cycles, and still checks payload hashes before use. It does not interpret arbitrary file paths or URLs from cache text. New Krea children disable Hub symlink/shared-blob layouts before imports without changing the parent or other backend environments. Missing required components stop readiness, and tokenizer/scheduler checks precede expensive transformer loading.

The installer uses its own Python environment with Torch 2.13.0 CUDA 13, Diffusers 0.42.1, Transformers 5.10.1, Hub 1.33.0, Accelerate 1.12.0, bitsandbytes 0.50.2 and PEFT 0.21.2. Remaining transitives follow those constraints. `pip check` and CUDA/VRAM/import preflight do not constitute a GPU dependency vulnerability audit or proof of inference correctness. CI imports pinned custom modules, loads the pinned tokenizer/scheduler and a tiny fixture checkpoint in disposable CPU scratch without neural model weights/CUDA packages. Basic native 832 × 480 INT8 generation and pause/reset passed in a short live A100 40 GB run; the README records timings, high memory use and allocator retries. Cold-start/long-session reliability and a complete GPU-environment vulnerability audit remain unverified. The SD-Turbo/Waypoint stacks are not replaced.

Krea reuses the same worker, single-controller slot, token gate and ACK-limited delivery as the other modes. It waits for a controller configuration and ACK negotiation before inference, queues at most one decoded chunk, and stops generation retries after failure. Clip reset/reconnect cleanup runs behind owned GPU work. Its Colab tunnel has no token by default, matching the other notebooks. Setup refuses an already occupied bridge port and does not terminate other servers.

The INT8 input-shape adapter wraps only the loaded Krea transformer's `Linear8bitLt` modules. It flattens rank-4/higher activations for matmul and restores their output shape without replacing quantized weights, patching installed vendor code or altering global Torch functions. Separately, the startup Fast profile uses outlier threshold 0 (no FP16 outlier correction); Balanced retains threshold 6. Fast can change image quality. Invalid profiles fail before model downloads/loading. The engine label reports the selected profile.

Krea and LTX children default to expandable CUDA allocator segments; either explicit user allocator alias is retained and the launcher parent/SD-Turbo/Waypoint environments are unchanged. The Krea warning filter suppresses only duplicate instances of the exact pinned bitsandbytes cast-warning template, retaining the first per dtype and all other diagnostics. Optional GPU validation/benchmark commands use the existing runtime and model cache; they do not install another environment or start a public listener. Benchmark reports/images are retained in the requested output folder and existing reports are not overwritten.

Fast also applies PyTorch's Conv3d-only VAE weight memory-format conversion; dimensions and values are retained and non-convolution parameters are untouched. Balanced loads the original layout. No new dependency or model distribution is introduced. The README records matched native-resolution A100 timings; these short comparisons do not establish long-session quality or cold-start reliability.

## Workstation access

`workstation.py setup` creates its own environment rather than modifying system Python. It reuses the same legacy model dependency pins listed above, with a selected CUDA Torch wheel and patched Pillow/filelock/setuptools. The CPU dependency audit does not establish security of this GPU environment.

`setup --backend waypoint` instead uses `.workstation-waypoint` and the same pinned Waypoint installer/adapter as Colab. The two backend environments cannot be reused as one another's setup target. An incomplete install is marked not ready, and launch verifies the backend/runtime revision and dependency signature before GPU startup. Optional `--prompt-seeds` is recorded at setup and controls the child's seed-generator feature flag; it does not install the legacy SD-Turbo application stack. `--prompt-seed-model` accepts only the two fixed models, persists at setup or overrides the child at start, and requires prompt seeds to be enabled. The dependency and model-license limitations in the Waypoint section still apply, including SD-Turbo/SDXL-Turbo's separate commercial-use terms for optional prompt seeds. Native workstation Waypoint GPU inference remains unverified.

Waypoint model/Inductor/Triton caches persist in its runtime or the explicitly selected model-cache folder; auth locations are preserved. Launch settings are applied to the child environment only, and the launcher's own backend, listener and pairing-token fields take precedence. A setup/start for one backend does not stop other servers or rewrite another backend's installation. LAN setup skips tunnel downloads; Cloudflare uses the existing on-demand downloader. Pairing tokens are separate per managed runtime, at its `access-token` file, and Waypoint logs are under its `bridge_logs` folder.

The workstation launcher requires a persistent random token, stored in `.workstation/access-token` (owner-only permissions on Linux; inherited user-folder permissions on Windows). The client must authenticate before receiving a welcome message, submitting controls, receiving video, or taking the single controller slot. The token is not placed in URLs, server arguments, health responses, snapshots, or server/tunnel logs. It is displayed in the launching terminal for pairing.

Use direct `ws://` only over trusted LAN/VPN connections. For internet use, choose the TLS Cloudflare transport or a VPN; the token does not encrypt plain WebSocket traffic. Cloudflare mode binds to loopback unless explicitly overridden. No firewall or router settings are modified automatically. The existing Colab setup remains compatible with a blank token; it does not gain workstation authentication automatically.

TouchDesigner saves the entered access token in the project/component parameters. Clear it before sharing a paired `.toe` or `.tox` file. Distributed project builds contain an empty token. Only connect to server URLs you trust.
